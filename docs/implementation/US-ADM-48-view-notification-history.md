# US-ADM-48 — View Notification History

## User Story

As an authenticated administrator, I want to view a paginated history of notifications generated by SaludVital so that I can monitor communications sent to patients and identify their processing and delivery statuses.

## Acceptance Criteria

1. Only authenticated administrators can access notification history and its protected endpoint.
2. The page retrieves persisted notification rows through the existing notification dashboard service and model.
3. The history displays Fecha, Canal, Destinatario, Tipo, Mensaje, Estado, and Acciones.
4. WhatsApp, email, and SMS use persisted channel values. An internal system channel is unavailable because it is not supported by the notification schema.
5. Rows show the recorded date, event type, masked destination, patient name when associated, a safe preview when available, and the stored application status with provider status kept separate.
6. Patient name is limited to the associated patient and destination values are masked. Raw notification payloads, clinical text, provider identifiers, and raw errors are not returned.
7. Provider acceptance is displayed separately from provider-confirmed delivery.
8. Rows are sorted by `COALESCE(sent_at, created_at)` descending, with ID descending as a stable tie-breaker.
9. Server-side pagination remains bounded to eight records per page.
10. Mobile uses compact cards with the same history fields rather than a squeezed desktop table.
11. Pagination, loading, empty, unavailable-channel, and error states are included.
12. User-facing text remains Spanish and follows the SaludVital notification dashboard design.
13. Message previews are inserted with `textContent`; row details use keyboard-accessible native disclosure controls.
14. No delete, resend, or status-changing action is implemented.
15. Unit, integration, browser, and accessibility tests cover the history behavior.

## Implementation Notes

- Reused `/admin/notifications`, `/api/admin/notifications`, administrator authorization, `Notification`, its patient association, and the US-ADM-47 dashboard UI. No extra route, model, table, or dependency was added.
- Email and SMS previews are concise text built from the persisted event type, date, and time. The query extracts only those JSON fields; doctor and specialty details are omitted from the preview.
- WhatsApp message body is a provider-managed template and is not persisted locally. The interface clearly states that the exact template text is unavailable instead of inventing it.
- Internal system notifications have no distinct persisted channel and cannot be listed separately.
- “Ver detalles” expands the application and provider statuses and a fixed, non-sensitive failure explanation. It does not mutate a notification.
